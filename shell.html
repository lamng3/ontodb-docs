    Using OntoDB

    Shell reference

    The shell is OntoDB's interface. It reads SPARQL and backslash commands from standard input and prints results to standard output.

    On this page
    1. Starting the shell
    2. How input is read
    3. Commands
    4. Results and errors
    5. Sessions

    Starting the shell

    ontodb [--strict] [--db] [dir]
    InvocationDatabase
    ontodbIn memory. Nothing is kept after \quit
    ontodb dir or ontodb --db dirPersistent, in dir, created if missing. The first line reports what was recovered
    ontodb --strict dirPersistent, but refuses to open if the log is damaged

    The shell reads standard input, so a script can be piped in: ontodb mydb < script.txt. The prompt OntoDB> is printed before each statement whenever the shell reads standard input, piped or not; with sessions it shows the session number, OntoDB:2>.

    How input is read

    • A line that starts with \ is one shell command.
    • Anything else is SPARQL. A statement may span lines and runs when its { } group has opened and closed and every string is closed. A PREFIX line stays pending until the query that uses it is complete.
    • # starts a comment, except inside a string or an IRI, so <http://example.edu/univ#Student> is read whole.
    • \quit leaves at once, even in the middle of a statement.

    Commands

    CommandWhat it does
    \load pathLoads a Turtle (.ttl), N-Triples (.nt), or RDF/XML (.rdf, .owl) file. In a persistent database the whole file is one transaction
    SPARQL statementRuns a query or an update. In a persistent database an update is one transaction
    \explain queryPrints the plan without running it
    \explain analyze queryRuns the query and prints each plan node with its estimated and actual rows, then the time
    \checkpointPersistent databases: writes a snapshot and empties the log
    \verifyPersistent databases: checks the snapshot and log, rebuilds from them, and compares with the live database
    \log [n]Persistent databases: prints the last n log records (default 20), oldest first
    \crashPersistent databases: exits immediately without flushing, to test recovery
    \hindex build, \under, \vload, \vindex build, \similarSemantic search: label the class hierarchy, list what is under a class, read vectors, build indexes, find the nearest terms. See Semantic search
    \statsPrints page, buffer, and log counters
    \timing on or offPrints each statement's time after its result
    \setPrints the settings
    \set knob valueChanges a setting. See Settings
    \session nSends the following input to session n, creating it if needed
    \helpLists the commands
    \quit, \qLeaves the shell

    In an in-memory database, \checkpoint, \log, and \crash answer not built yet, and \verify says there is nothing on disk to verify.

    \bpm and \page <id> inspect the buffer pool; with the default memory backend they answer no buffer pool. \trace on|off prints component events to stderr. \tree spo and \tree spo dot draw an index on the indexed backend. \begin, \commit, and \abort run an explicit transaction in the current session; \txns and \locks list transactions and the lock table.

    Results and errors

    A query prints its variables on one line, then one row per line in canonical spelling (<iri>, "literal", "lex"@en, "lex"^^<datatype>, _:blank), then a row count. An update prints how many triples it changed: inserted 1 triple, deleted 0 triples.

    A statement never crashes the shell. A parse or bind error prints its line and column; any other failure prints error: and a message. See Messages and troubleshooting.

    Sessions

    \quit, \help, and \session run on the main thread. Every other command runs on the current session's worker thread. Sessions share one database. Until transactions are built, sessions are separate prompts, not isolated transactions.
