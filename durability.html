    Internals

    Disk persistence design

    The page-based store keeps a database file of 4 KiB pages plus a write-ahead log. Deletes shrink the B+ tree in place, and a scan freezes only the triples it already copied. For the persistent databases that run today, see Persistent databases.

    On this page
    1. Persistence
    2. Reclaiming space
    3. What a snapshot is here

    Three words get borrowed from log-structured stores and do not name three background jobs here. Persistence is a snapshot plus the log for the shell's databases, and the database file plus the log for the page store. Space comes back when a delete merges or reuses a slot. On the page path, a snapshot is a copied scan result or a lock held until commit. The persistent databases that run today keep a different, simpler pair of files; see Persistent databases.

    Persistence

    Two files. This is the page path, plans 1.1, 3.6, and 8.3 to 8.7.

    The database file is a sequence of 4096-byte pages. DiskManager owns it. Page ids survive restart. Each page image starts with an 8-byte pageLSN. The catalog, page 0, records the header page of spo, pos, and osp, and the dictionary's root. Term spellings live in the term heap, which is more pages in that same file. Triple keys live in the B+ tree leaves.

    The log is a separate append-only file. LogManager is constructed with a log_path. Append assigns an LSN. Flush makes every record up to that LSN durable. Commit forces the commit record. That commit record is the acknowledgement a later open will trust.

    Status

    The page path runs and recovers from crashes in the tests and the crash harness (WAL and ARIES). The shell does not open it from a directory yet: ontodb <dir> is durable through its own snapshot and log; see Persistent databases.

    A clean close and a crash are different successes.

    A clean close is plan 3.6. Flush every dirty frame, flush the catalog, then ShutDown the file. The next process reads the pages and does not need the log. An unflushed dirty frame is a lost triple even when nobody crashed.

    A crash is the recovery feature. The policy is steal / no-force, described in WAL and ARIES. An uncommitted page may already be on disk. A committed page may not be. Redo installs committed history the pages missed. Undo removes loser triples the pages kept. \crash exits without flushing, which is how you test that path on purpose.

    What becomes durable, and when:

    EventDurable after
    Insert still in a transactionthe log record, only if a dirty page was stolen and the WAL rule flushed first
    \committhe commit record is on the log
    Checkpointevery dirty page, then the checkpoint record (the checkpoint is sharp)
    Process exit through ShutDownevery dirty page and the catalog
    \crashonly what a previous flush already wrote

    The shell knobs pool_size and lru_k change which pages stay in memory. They do not change the file format.

    Planned

    Plan 1.1 created the database file, plan 3.6 the clean restart, and plans 8.1 through 8.7 the log, the WAL rule, and crash recovery. The clean close came first, so a shutdown bug was never mistaken for a recovery bug.

    Reclaiming space

    The index is one B+ tree per permutation. A key lives in exactly one leaf of that tree. A delete removes the key and then merges or redistributes so every node except the root stays at least half full. That work finishes inside BPlusTree::Remove, before the call returns. There is no later job that rewrites sorted runs.

    A missing key deletes nothing. A removed key does not stay behind as a marker for a reader to skip. Readers of a leaf see the keys that are still there. Crash recovery can still undo that delete, by the logical triple record and a CLR, if the transaction did not commit. The leaf after recovery contains the key again because undo put it back, not because a tombstone was compacted away.

    The term heap is looser. Delete on a heap page frees a slot, and a later insert may reuse it. FreeSpace counts that hole. Nothing in the plan rewrites a heap page to slide the survivors together, so a page can stay sparse when the hole is smaller than the next spelling. Deleting a triple does not drop the spelling. The dictionary keeps the id, a later insert of the same IRI gets that same id, and a log record written earlier still names it.

    Bulk load is the other time the tree gets dense. Plan 2.6 builds full leaves from keys that are already sorted. Plan 6.1 does that at \load instead of inserting one triple at a time. Random Insert leaves a lower fill factor. That is a property of the tree you built, not a debt a compactor will come back to pay.

    Leaf compression is smaller keys inside a leaf, delta-encoded the RDF-3X way. It has no stub. It changes Compare and the prefix bounds. It is a page layout, written when the leaf is written, not a background rewrite of old levels.

    On the memory path, \checkpoint already empties the log, because the snapshot holds everything before it. On the page path, the log grows for the life of the database today. A checkpoint tells recovery where redo can start. It does not delete bytes in front of that LSN, and analysis still reads the whole file to find losers that began before it. Truncating the log after a checkpoint, once no active transaction or dirty page still needs the older records, is the natural follow-on of plan 8.5. Do it only after redo's starting LSN is real, or you will throw away the record that would have repaired a stolen page.

    Which permutations exist is the other space decision. Plan 3.5 measures before adding POS or OSP. A permutation you do not build does not need a compaction policy.

    Planned

    The delete path is slice 2.7. The heap slot is slice 3.1. Bulk load is slices 2.6 and 6.1. Leaf compression comes after you can say what it does to prefix bounds, and the note belongs in a writeup.

    What a snapshot is here

    MemStore::Scan copies the matching triples into the iterator and then drops the mutex. Inserts and deletes that happen after Scan returns do not change that iterator. The copy is one pattern's result, held for one operator. It is not a named database snapshot, and it is not repeatable across a second Scan in the same query. The indexed iterator does not copy the tree. It copies one leaf's remaining keys and holds no latch or pin between rows, so a concurrent split or merge is handled by latch crabbing (plan 7.1) and kept empty leaves, not by a frozen view.

    On the memory path, \checkpoint is a real snapshot: the whole database at one LSN, and the next open starts from it. On the page path, \checkpoint writes a checkpoint record: the active transactions, and the LSN recovery may start from. A blocking checkpoint waits until writers are quiet and can force dirty pages. A fuzzy checkpoint does not wait, and it must record the dirty-page table. Either way, a SPARQL query does not read "as of" that checkpoint. Open after a crash does.

    Repeatable read holds shared locks on the keys you read until commit. That keeps those triples from changing. It does not freeze the store. An insert of a triple you did not lock can still appear in a second scan. That is the phantom in plan 7.6. Serializable adds a range lock, a gap lock, or a predicate lock so the insert waits. The frozen set is the lock set, not a timestamp.

    A versioned snapshot, where a reader ignores locks and sees the store as of its start timestamp, is the MVCC design. It has no stub. If you build it, old versions have to stay until every reader that might need them has finished, and only then can a delete drop the version. That reclamation is part of the design you write down before the code, then measure, then cite from a writeup. It is not a job the B+ tree already runs.
